# PanacheUI — Color Theory & Theme System

**This document is the one-stop reference for every color, theme, and color-theory concept
used by PanacheUI and its consumer plugins.**

The color pipeline that Panache ships with comes from **ColorSchemeCreator v2**
(`D:\Visual Studio Code Projects\ColorSchemeCreator`) — a purpose-built tool that generates
palettes in OKLCH, validates them against WCAG + APCA contrast rules, and exports theme JSON
in a schema Panache reads natively.

Panache adopted the **v3 slot vocabulary** on 2026-07-10 (Material 3 + Radix + Fluent 2
style — 66 slots covering surfaces, elevation ladders, accent triads with state variants,
semantic status quads with containers, borders, state layers, a rarity ladder, glows, and
row highlights). Panache no longer accepts v2 (legacy 33-slot Base/Panel/Accent-only) theme
files — the loader will log a warning and skip them.

### Purpose
- Before writing a color into a plugin, read this doc — the correct slot almost certainly
  already exists.
- Before authoring a new theme, read this doc — the slot list, the validation rules, and the
  design proportions are all here.
- Before touching `PanacheTheme.cs`, `ThemeDto.cs`, `ThemeLoader.cs`, `ThemeIpc.cs`, or the
  `Theme.*` aliases in `PanacheComponents.cs`, read this doc.
- When new color theory enters the pipeline (a new harmony, a new rule, a new slot family),
  add a section here immediately.

## 1. System Overview

Panache separates color into three layers:

```
┌─────────────────────────────────────────────────────────────────┐
│  Layer 1  Theme file        Themes/<Name>/theme.json            │
│           (or built-in)     Generated by ColorSchemeCreator v3  │
│                             OR hand-authored partial override   │
└─────────────────────────────────────────────────────────────────┘
                                     │  Parsed by ThemeLoader.cs
                                     ▼
┌─────────────────────────────────────────────────────────────────┐
│  Layer 2  PanacheTheme      Immutable C# record — 66 PColor     │
│           registry          slots (v3 vocabulary). Legacy V1    │
│                             names still resolve via computed    │
│                             property aliases. PanacheThemes.    │
│                             Active is current; ActiveChanged    │
│                             fires on swap.                      │
└─────────────────────────────────────────────────────────────────┘
                                     │  Read by consumers
                                     ▼
┌─────────────────────────────────────────────────────────────────┐
│  Layer 3  Consumers         PUI.SectionWrap, PUI.Card,          │
│           (this plugin +    PUI.PillButton snapshot the theme   │
│           every downstream) once at init; downstream plugins    │
│                             (GlamourDresserHelper, CraftQueue,  │
│                             etc.) read via PanacheThemes.Active │
│                             or the Dalamud IPC surface.         │
└─────────────────────────────────────────────────────────────────┘
```

Consumers **must not** re-read `PanacheThemes.Active` per frame. Snapshot it once at init and
resubscribe on `PanacheThemes.ActiveChanged`. The static property is cheap but the rule keeps
consumer code honest about where the palette lives.

The theme file is the source of truth. Everything else — the DTO, the merger, the registry,
the IPC surface, the legacy V1 aliases — is plumbing that carries the palette from JSON to
`SKPaint.Color`.

## 2. OKLCH — the Perceptually Uniform Color Space

ColorSchemeCreator generates every color in **OKLCH**, not RGB or HSL. Panache stores the
same colors as `PColor` (RGBA), but understanding the space they were designed in is
essential to authoring new palettes and reasoning about why a color "looks right" at a given
lightness.

### The three axes

| Axis | Range | Meaning |
|-----|-------|---------|
| **L** — Lightness | `0.0` (black) → `1.0` (white) | **Perceptually uniform.** A patch at L=0.5 always looks mid-gray regardless of hue. HSL fails here — HSL yellow at L=50 reads near-white, HSL blue at L=50 reads near-black. |
| **C** — Chroma | `0.0` (gray) → `~0.4` (max) | Saturation / colorfulness. Max C is hue-dependent (blues cap ~0.35, reds ~0.37) and drops sharply near L=0 and L=1. Not every (L, C, H) triple is inside sRGB. |
| **H** — Hue | `0°`–`360°` | Color angle. `0°`=red, `120°`=green, `240°`=blue. Same as HSL/HSV hue conceptually. |

### Why OKLCH over HSL / RGB

1. **L is perceptually uniform.** A lightness ramp (Surface0 → Surface1 → Surface2 →
   Surface3 → Surface4) that steps `L` by `+0.03` each looks like an even elevation ladder —
   regardless of hue tint. The same ramp in HSL L looks lumpy because yellow at HSL 50% is
   far brighter than blue at HSL 50%.
2. **C is decoupled from L and H.** You can hold a color's *color-ness* constant while
   sweeping its brightness (e.g. Primary → PrimaryHover → PrimaryPressed → PrimaryDisabled).
   HSL S does not do this.
3. **APCA / WCAG 3 alignment.** The next-generation accessibility model (APCA Lc) is
   designed for perceptually-uniform spaces; OKLCH gives us a direct hook.
4. **Predictable gamut mapping.** Colors outside sRGB are reduced along the chroma axis
   (holding L and H fixed) via a CSS Color 4 binary search — the resulting color still has
   the intended lightness and hue.

### Conversion pipeline

```
#RRGGBB
  → sRGB [0,1]              (divide by 255)
  → Linear RGB              (undo gamma ~2.4)
  → OKLab (Ottosson matrices)
  → OKLCH                   (polar transform of Lab)
```

The inverse walks the same chain backwards. In ColorSchemeCreator these live in
`core/oklch.py::hex_to_oklch` / `oklch_to_hex`. If Panache ever needs OKLCH math at runtime
we should port those two functions — they're the only bridge you need.

### Gamut mapping (CSS Color 4)

When an out-of-gamut color is requested (e.g. `oklch(0.75 0.30 195)` — pure cyan is too
chroma-heavy for sRGB), the mapper:

1. Detects out-of-gamut (converts to linear RGB, verifies channels ∈ `[-1e-6, 1+1e-6]`).
2. Binary-searches `C` downward (holding `L` and `H` fixed) until the color fits.
3. Compares that result to a naive channel-clip in RGB. If ΔE_OK between the two is under
   the **JND threshold (0.02)**, uses the cheaper clip; otherwise uses the binary result.

The takeaway: **L and H are always preserved; C is what gets reduced.** That is why every
Panache slot has an L range and a C range, but hue is either "any" or "harmony-placed".

### The helpers

Every derived-color operation Panache might need has a name:

| Function | What it does |
|----------|-------------|
| `rotate_hue(hex, deg)` | Preserve `L` + `C`, shift `H`. Powers every harmony. |
| `with_lightness(hex, L)` | Preserve `C` + `H`, set `L`. Powers hover/pressed/disabled variants and elevation ladders. |
| `with_chroma(hex, C)` | Preserve `L` + `H`, set `C`. Powers "muted" text variants and disabled states (chroma reduced ~50%). |
| `sweep_lightness(hex, [L₀, L₁, ...])` | Tonal ramp — one hue, N brightnesses. Material-3 style. |
| `tint_neutral(base, accent, chroma=0.02)` | The **"warm gray" trick.** A neutral gray whose hue leans towards the accent at very low chroma (0.01–0.06). This is why every Panache Surface0..4 has a subtle tint pulling toward the accent hue — pure neutrals feel cold and disconnected from the palette. |

## 3. Harmonies — 16 Accent-Placement Strategies

Every roll picks a **harmony**, which decides how the two accent hues (`Primary` and
`Secondary`) are placed relative to a randomly-chosen `base_hue`. Every other slot roams
freely — coherence comes from **relationships** (contrast ratios, hue gaps, lightness
stepping) enforced by the rules engine, not from every slot sitting on a canonical hue.

Result: `Primary` might be teal on one roll and magenta on the next. Readability is
guaranteed by the rules engine regardless.

### The classical 8

| Harmony | Primary offset | Secondary offset | Effect |
|---------|--------------:|-----------------:|--------|
| Complementary | +180° | +210° | Base + opposite + nearby |
| Analogous | +30° | −30° | Base + two neighbors within ±30° |
| Triadic | +120° | +240° | Three hues evenly spaced |
| Split-Complementary | +150° | +210° | Base + two hues flanking the complement |
| Square (Tetradic) | +90° | +270° | Four hues at 90° intervals |
| Pentadic | +72° | +144° | Five hues at 72° |
| Monochromatic | 0° | 0° | All on base hue; distinction from S / L variation |
| Rectangular Tetradic | +60° | +240° | Asymmetric 4-color grid |

### The modern 8

| Harmony | Primary offset | Secondary offset | Effect |
|---------|--------------:|-----------------:|--------|
| Accented Analogous | +30° | +180° | Analogous base + one complement (signal + rest) |
| Compound | +150° | +30° | Split-complement + neighbor |
| Analogous-Complementary | +30° | +180° | Neighbor + direct complement |
| **Warm-Cool Split** | *see below* | *see below* | Base forced into warm (15–55°) or cool (200–250°); accents in opposite band. Coin-flip polarity. |
| Achromatic Accent | 0° | 0° | Grayscale base (S=0–3) + one saturated accent — "signal + rest" extreme |
| Simultaneous Contrast | +180° | +90° | Complement + right-angle — optical vibration |
| Solarized-Symmetric | +180° | +210° | Complement anchor; L symmetric so light and dark themes mirror |

Beyond the 16 automated harmonies, ColorSchemeCreator supports `harmony: manual` — a
hand-crafted palette (like the `Shadow` default). Manual themes typically fail one or two
rules (they're intentional design choices, not algorithmic outputs), and that's fine — the
rules exist to guide algorithmic generation, not to gate handcraft.

### Accent lightness / saturation

Independent of hue placement, the accents' `L` and `C` follow the theme mood:

- **Dark theme** (`Surface0 L ≤ 0.18`): Primary L ∈ [0.50, 0.72], S ∈ [55, 90] → C ∈ [0.176, 0.288]
- **Light theme** (`Surface0 L > 0.18`): Primary L ∈ [0.30, 0.55]

The chroma mapping (a legacy HSL S 0–100 fed through the pipe) is `C = S × 0.32 / 100`. So
S=100 caps at C=0.32 — near the max chroma OKLCH can express before gamut clipping bites.

### Semantic status hues

Unlike V1 (where the five status slots roamed by hue), **v3's semantic status slots have
canonical hues**. `Success` ≈ 140° (green), `Warning` ≈ 40° (yellow-orange), `Error` ≈ 5°
(red), `Info` ≈ 215° (blue). Meaning stays stable across every theme — a green success chip
never becomes red because the harmony changed. Each has a `.Container`, `.On<Name>`, and
`.On<Name>Container` derived by the same formulas as `Primary`.

### Genre presets

Applied **after** the retry loop (so the rules can't undo them). Six presets:

| Preset | Effect |
|--------|--------|
| **None** | No-op — pure harmony output. |
| **Horror** | Desaturate everything to C < 0.05 except `Warning` (blood red at C≈0.20, H=25°). |
| **Cyberpunk** | Full override — purple-tinted bg stack (L 0.06–0.17, H=290), neon cyan accent (L=0.78, C=0.28, H=195). Forces dark. |
| **Fantasy** | Full override — warm brown bgs (H=40°, C=0.03–0.04), gold Tertiary, burnished accents. Forces dark + warm. |
| **Noir** | Full monochrome (C=0) except `Primary` at max chroma. Grayscale elevation ladder. |
| **Solarized** | Earth-tone neutrals (H=45°, C=0.02) + moderate-saturation accents (C≈0.13). |

## 4. Rules Engine — 28 Validation Rules

Every generated palette is validated against 28 rules across six groups. Failed rules
trigger a retry loop (up to 6 per-slot retries × 3 full rolls). Only palettes that pass all
28 rules end up in an algorithmically-generated `theme.json`. Manual themes (like
`Shadow`) may intentionally fail a few — they're hand-crafted design choices.

Every ColorSchemeCreator export ships with a `rules_report.txt` documenting the exact
values against the thresholds — check any theme's `rules_report.txt` for a worked example.

The rule names below still reference V1 slot names (`Base`, `Panel`, `TextHi`, etc.) —
that's how the tool prints them. V1 → v3 slot mapping is documented in §6.

### Group 1 — WCAG 2 contrast (9 rules)

Ratio = `(L1 + 0.05) / (L2 + 0.05)` where L1 > L2, L = WCAG relative luminance. Range 1.0–21.0.

| Rule | Foreground (V1 → v3) | Background (V1 → v3) | Threshold |
|------|-----------|-----------|-----------|
| TextHi over Base | OnSurfaceHi | Surface0 | ≥ 4.5 |
| TextHi over Panel | OnSurfaceHi | Surface3 | ≥ 4.5 |
| TextMed over Panel | OnSurfaceMed | Surface3 | ≥ 4.5 |
| TextMuted over Panel | OnSurfaceLow | Surface3 | ≥ 3.0 |
| TextDim over Panel | OnSurfaceDisabled | Surface3 | ≥ 2.0 |
| GearName over Panel | Tertiary | Surface3 | ≥ 4.5 |
| Accent over Panel | Primary | Surface3 | ≥ 3.0 |
| AccentAlt over Panel | Secondary | Surface3 | ≥ 3.0 |
| White ✕ over CloseFill1 | #FFFFFF | Error | ≥ 3.0 |

### Group 2 — APCA Lc (8 rules)

APCA is the WCAG 3 candidate and models dark-mode contrast far more accurately. Lc scale:

| Lc | Meaning |
|----|---------|
| 90 | Preferred body text |
| 75 | Minimum body text |
| 60 | Non-body / labels |
| 45 | Headlines |
| 30 | Spot-readable (disabled) |
| 15 | Invisible |

| Rule | Threshold |
|------|-----------|
| TextHi over Base (body) | Lc ≥ 75 |
| TextHi over Panel (body) | Lc ≥ 75 |
| TextMed over Panel (body) | Lc ≥ 75 |
| GearName over Panel (body) | Lc ≥ 75 |
| TextMuted over Panel (label) | Lc ≥ 60 |
| Accent over Panel (label) | Lc ≥ 60 |
| AccentAlt over Panel (label) | Lc ≥ 60 |
| TextDim over Panel (spot) | Lc ≥ 30 |

### Group 3 — layer separation, CIE L* delta (4 rules)

Adjacent surfaces must be visually distinct. Uses **CIE L*** (perceptual lightness derived
from WCAG relative luminance), not OKLCH L, because the L* threshold values are calibrated
against decades of graphic-design literature.

| Rule | Threshold |
|------|-----------|
| Base ↔ Panel (Surface0 ↔ Surface3) | ΔL* ≥ 1.5 |
| Panel ↔ Panel2 (Surface3 ↔ Surface1) | ΔL* ≥ 0.5 |
| Panel ↔ CardBg (Surface3 ↔ Surface3) | ΔL* ≥ 1.5 |
| Stripe1 ↔ Stripe2 (Surface2 ↔ Surface1) | ΔL* ≥ 1.0 |

L* formula: `L* = 116 × y^(1/3) − 16` for `y > 0.008856`, else `L* = 903.3 × y`, where `y`
is WCAG relative luminance.

### Group 4 — glow visibility (2 rules)

Glow slots (`GlowPrimary`, `GlowSecondary`) need enough absolute luminance to *shine* on
top of Surface0, not blend in.

| Rule | Threshold |
|------|-----------|
| GlowGold luminance (GlowPrimary) | Y ≥ 0.55 |
| GlowCyan luminance (GlowSecondary) | Y ≥ 0.55 |

Y is WCAG relative luminance = `0.2126 × R_lin + 0.7152 × G_lin + 0.0722 × B_lin`.

### Group 5 — status distinctness (3 rules)

The status colors must be visually distinguishable and each readable on Panel.

| Rule | Test | Threshold |
|------|------|-----------|
| Min status hue gap | Closest pair among all 5 (Success/Warning/Error/Info + one) | ≥ 18° |
| StatusOk ↔ StatusMiss hue gap | Success vs. Error specifically | ≥ 90° |
| Weakest status over Panel | Minimum WCAG ratio across the semantic set | ≥ 3.0 |

Hue gap: `min(|a − b|, 360 − |a − b|)` ∈ `[0, 180]`.

### Group 6 — warning legibility (2 rules)

| Rule | Threshold |
|------|-----------|
| Warning over Base (Warning ↔ Surface0) | ≥ 4.5 |
| WarningMuted over Panel (WarningContainer ↔ Surface3) | ≥ 3.0 |

### The retry loop

`core/harmony.py::roll_until_pass`:

1. Full random `roll()` → apply to palette.
2. Evaluate all 28 rules.
3. If any fail:
   - Collect each failing rule's `fix_key` (the slot to re-roll).
   - Call `_push_slot(slot)` — samples 30 candidates within the slot's family-defined L / C
     ranges, verifying both WCAG and APCA constraints; for status slots additionally
     enforces min 42° gap from all other status hues; fallback to a forced extreme after 30
     attempts.
   - Repeat up to `per_slot_retries` (default 6).
4. If still failing, another full `roll()` (up to `full_retries` = 3).
5. Apply the genre preset (if any) *after* all retries.
6. Return best-effort palette.

If a shipped `theme.json`'s `meta.rules.failed > 0`, that palette either hit the retry
ceiling (regenerate) or was hand-crafted with `harmony: manual` (leave alone).

## 5. V3 Slot Vocabulary — Panache's Canonical 66

The 66 slots on `PanacheTheme.cs` are the runtime API. Every external plugin reads via
these slot names. Do not rename them without coordinated updates to every consumer.

Slots follow **Material 3 + Radix + Fluent 2** conventions — every accent gets Hover /
Pressed / Disabled / Container variants for free; every accent has an `On<X>` companion
sized for icon/label use and an `On<X>Container` sized for body text; semantic status
colors carry canonical hues; borders and state layers are first-class instead of
opacity-derived at draw time.

### Surfaces (6) — the elevation ladder

Every surface slot carries a subtle tint of the accent hue (via `tint_neutral` with
C≈0.02) — pure neutrals feel cold and disconnected. The lightness values step
monotonically (`Surface0 → Surface4` ≈ +0.03 L per step) so adjacent surfaces stay visually
distinct.

| Slot | Role |
|------|------|
| **Surface0** | Root window background — the darkest surface. |
| **Surface1** | First elevation above Surface0. Alt-row bottom, inner card. |
| **Surface2** | Second elevation. Alt-row top. |
| **Surface3** | Third elevation — the typical "panel" surface. |
| **Surface4** | Highest elevation. |
| **SurfaceInverse** | Inverted-L surface — tooltips, snackbars, banners. |

Header gradients must always end at `Surface3` so they bleed into the first section
seamlessly (see `../CLAUDE.md` and `docs/UMBRA_VISUAL_TECHNIQUES.md`).

### On-surface text (4) — the contrast ladder

Chosen so that `OnSurfaceHi` sits at the opposite lightness extreme from `Surface0`.
Saturation drops as text importance falls.

| Slot | Role |
|------|------|
| **OnSurfaceHi** | Primary body text. |
| **OnSurfaceMed** | Secondary body text. |
| **OnSurfaceLow** | Tertiary text — small labels, badges. |
| **OnSurfaceDisabled** | Placeholder / disabled. Also used for "very subtle" text. |

### Primary accent (7) — the brand color + state variants + container

`Primary` is the main brand accent (harmony-placed, §3). Its state variants and container
are derived automatically by ColorSchemeCreator (§6 has the formulas).

| Slot | Role |
|------|------|
| **Primary** | The main brand accent. Buttons, pill borders, section left-bars. |
| **PrimaryHover** | Primary at L ± 0.05. Hover state. |
| **PrimaryPressed** | Primary at L ± 0.10. Pressed state. |
| **PrimaryDisabled** | Primary at L ≈ 0.35 with C reduced ×0.4. Disabled state. |
| **OnPrimary** | Foreground for icon/label placed on top of `Primary`. Guaranteed APCA Lc ≥ 60. |
| **PrimaryContainer** | Low-chroma tint of Primary (L≈0.20 dark / 0.92 light; C ≤ 0.08). Chip bg, callouts, subtle brand-tinted surface. |
| **OnPrimaryContainer** | Body-text-safe foreground on top of `PrimaryContainer`. APCA Lc ≥ 75. |

Standard opacity conventions when applied to a UI element:

| Use | Opacity |
|-----|---------|
| Left accent bar | 0.70 |
| Top section highlight | 0.18 |
| Section label | 0.65 |
| Card border | 0.22 |
| Pill button background gradient start | 0.18 |
| Pill button background gradient end | 0.08 |

### Secondary accent (7) — mirror of Primary

Same seven-slot structure, using a different harmony hue.

`Secondary`, `SecondaryHover`, `SecondaryPressed`, `SecondaryDisabled`, `OnSecondary`,
`SecondaryContainer`, `OnSecondaryContainer`.

Typical use: Special-Shop pills, alt-category glyphs, secondary-action buttons.

### Tertiary signal (4) — the "signal text" slot

Used for gear names, item names, callout text that needs to stand out but isn't a primary
action. Higher chroma than body text; no state variants (signal text doesn't get "pressed").

`Tertiary`, `OnTertiary`, `TertiaryContainer`, `OnTertiaryContainer`.

### Semantic status (4 quads × 4 slots = 16) — canonical, stable-meaning hues

Unlike V1's roaming status slots, these are **canonical**. Green = Success everywhere,
yellow-orange = Warning everywhere. Consumers can rely on hue.

| Family | Canonical H | Role |
|--------|------------|------|
| **Success** | ≈ 140° (green) | Success / done / positive |
| **Warning** | ≈ 40° (yellow-orange) | Warning / attention |
| **Error** | ≈ 5° (red) | Error / destructive |
| **Info** | ≈ 215° (blue) | Info / neutral / in-flight |

Each quad has four slots:
- `<Name>` — the bright semantic color.
- `<Name>Container` — the low-chroma container tint (chip bg).
- `On<Name>` — icon/label color on top of `<Name>`. APCA Lc ≥ 60.
- `On<Name>Container` — body-text color on top of `<Name>Container`. APCA Lc ≥ 75.

### Borders (4)

Derived from Surface1's lightness ladder. Use `BorderDefault` for most dividers,
`BorderSubtle` for barely-there, `BorderStrong` for card outlines that need to pop,
`BorderFocus` for the focus ring.

| Slot | Role |
|------|------|
| **BorderSubtle** | Surface1 + 1 step. Faint dividers. |
| **BorderDefault** | Surface1 + 2 steps. Standard card / row divider. |
| **BorderStrong** | Surface1 + 4 steps. Bold card outlines. |
| **BorderFocus** | Primary-hue at L≈0.65 dark / 0.45 light; C = min(0.20, Primary_C × 1.5). |

### State layers (4) — overlay tokens

Panache doesn't use draw-time opacity blends for hover/press — it uses discrete state
slots. This gives themes explicit control over hover feel.

| Slot | Semantic |
|------|----------|
| **StateHover** | Hover overlay. Surface0 + 2 steps. |
| **StatePressed** | Pressed overlay. Surface0 + 3 steps. |
| **StateSelected** | Selection highlight. = `PrimaryContainer`. |
| **StateFocused** | Focus ring. = `BorderFocus`. |

### Rarity ladder (6) — fixed hues, perceptually scaled

Meant for FFXIV item rarity strips (Common → Mythic). These slots have **canonical hues**
and don't roam even under harmony rolls — a legendary drop is always warm-orange.

| Slot | H | Dark L | Light L |
|------|--:|-------:|--------:|
| **RarityCommon** | 0° (gray) | 0.70 | 0.50 |
| **RarityUncommon** | 140° (green) | 0.65 | 0.45 |
| **RarityRare** | 240° (blue) | 0.60 | 0.42 |
| **RarityEpic** | 300° (purple) | 0.55 | 0.40 |
| **RarityLegendary** | 50° (orange) | 0.65 | 0.45 |
| **RarityMythic** | 90° (gold) | 0.75 | 0.55 |

### Glows (2) — the "shine" slots

Applied as inner-glows and sheens on Located rows (`GlowPrimary`, warm) and Hunt rows
(`GlowSecondary`, cool). Must have absolute Y ≥ 0.55 or they blend into the background.

Naming is by *role*, not hue — `GlowPrimary` might be an actual gold, or a pink-lavender,
or peach. The role is "warm signal glow".

### Row highlights (6) — background + border pairs

Three visual states for row-highlighting, each with a matched bg + border. Hues borrowed
from status semantics (Warning/Success/Info) at deep lightness so they read as *fills*
rather than *foreground colors*.

| Slot pair | Semantic |
|-----------|----------|
| `RowLocatedBg` / `RowLocatedBd` | Located this session (Warning-yellow tint) |
| `RowOwnedBg` / `RowOwnedBd` | Confirmed owned (Success-green tint) |
| `RowStoredBg` / `RowStoredBd` | Cabinet / retainer stored (Info-blue tint) |

## 6. Legacy V1 Aliases

Downstream plugins written before the v3 migration read `_theme.Base`, `_theme.Panel`,
`_theme.Accent`, etc. — the old 33-slot V1 vocabulary. Those names still resolve. Each is a
computed property on `PanacheTheme` forwarding to its v3 equivalent. Consumer code compiles
unchanged; new code should read the v3 slot directly.

**The aliases will be removed once every consumer is migrated.** New code that reads a V1
alias will need to be updated later; new code that reads the v3 slot won't.

### The mapping

| V1 alias | v3 backing slot | Notes |
|----------|-----------------|-------|
| `Base` | `Surface0` | |
| `Panel` | `Surface3` | |
| `Panel2` | `Surface1` | |
| `CardBg` | `Surface3` | (V1 CardBg and Panel were often near-identical) |
| `Stripe1` | `Surface2` | |
| `Stripe2` | `Surface1` | |
| `TextHi` | `OnSurfaceHi` | |
| `TextMed` | `OnSurfaceMed` | |
| `TextMuted` | `OnSurfaceLow` | |
| `TextDim` | `OnSurfaceDisabled` | |
| `TextSubtle` | `OnSurfaceDisabled` | (folded — v3 has no distinct "subtle") |
| `GearName` | `Tertiary` | |
| `Accent` | `Primary` | |
| `AccentAlt` | `Secondary` | |
| `StatusOk` | `Success` | |
| `StatusAct` | `Info` | (folded — v3's Info covers "active / in-flight" too) |
| `StatusRet` | `Info` | (folded — same semantic) |
| `StatusAtt` | `Warning` | |
| `StatusMiss` | `Error` | |
| `Warning` (V1) | `Warning` (v3) | Same slot name, same role |
| `WarningMuted` | `WarningContainer` | |
| `RowLocatedBg/Bd` | (unchanged) | Same slot names |
| `RowOwnedBg/Bd` | (unchanged) | Same slot names |
| `RowStoredBg/Bd` | (unchanged) | Same slot names |
| `CloseFill1` | `Error` | (red close button uses semantic red) |
| `CloseFill2` | `ErrorContainer` | |
| `CloseBorder` | `ErrorContainer` | (near-black red) |
| `GlowGold` | `GlowPrimary` | Rename — v1 named by hue, v3 by role |
| `GlowCyan` | `GlowSecondary` | Rename — v1 named by hue, v3 by role |
| `White` | (hardcoded `#FFFFFF`) | No longer a theme slot |

**Some V1 semantics folded** — most notably `TextSubtle` merges into `OnSurfaceDisabled`
and `StatusAct` / `StatusRet` both fold into `Info`. If a consumer was drawing meaningful
distinctions between those, it needs to explicitly pick a different v3 slot post-migration.

### Removed concepts

- **`StatusAct`, `StatusRet`, `TextSubtle`, `White` as theme slots.** V1 had these; v3
  merged, dropped, or hardcoded them. The aliases return sensible v3 substitutes but
  consumer code should migrate to the v3 slot it actually wants.
- **CloseFill / CloseBorder as a distinct color family.** V1 dedicated three slots to the
  close-button gradient; v3 just reuses `Error` + `ErrorContainer`, matching the semantic
  meaning ("this is destructive; use the red").

## 7. Design Proportions — 60 / 30 / 10

Every ColorSchemeCreator theme carries a `proportions` block that assigns each slot to one
of three "area weight" tiers — a classical **contrast of extension** (Itten) recipe.

**Read this as a design guideline, not a technical constraint.** When you're building a new
UI:

- ~60% of the pixel area should be dominant colors (surfaces + primary text).
- ~30% should be secondary text, muted containers, and row highlights.
- ~10% should be accents, status, glows, focus rings.

A UI that flips those proportions (accents everywhere, tiny bit of surface) reads as
"cluttered" or "screaming"; a UI that ignores the 10% band entirely reads as "washed out"
or "corporate". The rule is Itten's, not ours — it works.

Panache does not consume the `proportions` block at runtime today. Consult it when designing
a new window.

---

## 8. Semantic Tokens

Alongside `proportions`, every v3 theme carries a `tokens` block that groups slots by
intent — `surface`, `on_surface`, `brand_primary`, `status_success`, `status_error`,
`chrome_close`, etc. Use tokens to reference *intent* instead of *specific slot names* when
building a design system layer.

Panache does not currently expose the token dict at runtime — a future
`PanacheThemes.Active.Tokens` accessor would return this dict typed as
`IReadOnlyDictionary<string, IReadOnlyList<string>>`.

## 9. Theme File Format

Panache's `ThemeLoader` recognises **two shapes**. Both live under `Themes/`.

### Shape 1 — ColorSchemeCreator v3 export (folder per theme)

```
Themes/
  Shadow/
    theme.json          ← required
    preview.png         ← optional, informational only
    rules_report.txt    ← optional, informational only
```

`theme.json` structure:

```json
{
  "meta": {
    "name": "Shadow",
    "exported": "2026-07-10T20:11:45.758178",
    "harmony": "manual",
    "rules": { "passed": 21, "failed": 4 },
    "schema_version": "3.0"
  },
  "slots": {
    "Surface0": { "hex": "#0F0E12", "rgb": [15,14,18], "hsl": [255,13,6],
                  "oklch": { "L": 0.203, "C": 0.007, "H": 305.44 } },
    "Primary":  { "hex": "#E05C9A", ... },
    ...
  },
  "proportions": { ... },
  "tokens":      { ... }
}
```

Per-slot payload has:

| Key | Type | Notes |
|-----|------|-------|
| `hex` | `"#RRGGBB"` | The only field Panache currently reads. |
| `rgb` | `[R, G, B]` | 0–255 integers, informational. |
| `hsl` | `[H, S, L]` | Legacy HSL, informational. |
| `oklch.L` | `float` | 0.0–1.0, 4 decimals. |
| `oklch.C` | `float` | ~0.0–0.4, 4 decimals. |
| `oklch.H` | `float` | 0–360, 2 decimals. |
| `oklch_css` | `"oklch(L% C H)"` | Ready to paste into CSS (may be absent on some exports). |

`meta.name` (if present) wins over the folder name. `meta.rules.failed > 0` on a shipped
theme is either the retry-ceiling failure mode (regenerate) or a hand-crafted `manual`
palette (leave alone).

### Shape 2 — flat single-file theme (Panache's own partial-override format)

Drop `*.json` directly in the `Themes/` folder. Every field is optional; anything omitted
inherits from the theme named in `basedOn` (default: the built-in default).

```json
{
  "name": "ShadowRed",
  "basedOn": "Shadow",
  "primary": "#FF3060"
}
```

Field names are PascalCase-or-camelCase (Newtonsoft is case-insensitive by default); values
are hex strings — `#RGB`, `#RRGGBB`, or `#RRGGBBAA`.

This shape is meant for small user overrides (one color, no need to redefine 66 slots) and
for testing. Prefer Shape 1 for production themes so you get the OKLCH values and rule
validation report.

### Legacy v2 files are rejected

Panache detects legacy v2 exports (schema_version < 3.0, or `slots` block containing a
`Base` slot but no `Surface0`) and skips them with a warning:

```
[PanacheUI] Skipping legacy (pre-v3) theme file: Themes/OldTheme/theme.json
(schema_version=2.0). Re-export from ColorSchemeCreator v2+ with the v3 slot set.
```

Re-export from ColorSchemeCreator (make sure it targets v3), then drop the new folder in.

### The 66 v3 slots

| Group | Slots |
|-------|-------|
| Surfaces | Surface0, Surface1, Surface2, Surface3, Surface4, SurfaceInverse |
| On-surface text | OnSurfaceHi, OnSurfaceMed, OnSurfaceLow, OnSurfaceDisabled |
| Primary | Primary, PrimaryHover, PrimaryPressed, PrimaryDisabled, OnPrimary, PrimaryContainer, OnPrimaryContainer |
| Secondary | Secondary + Hover/Pressed/Disabled + OnSecondary + SecondaryContainer + OnSecondaryContainer |
| Tertiary | Tertiary, OnTertiary, TertiaryContainer, OnTertiaryContainer |
| Success | Success, SuccessContainer, OnSuccess, OnSuccessContainer |
| Warning | Warning, WarningContainer, OnWarning, OnWarningContainer |
| Error | Error, ErrorContainer, OnError, OnErrorContainer |
| Info | Info, InfoContainer, OnInfo, OnInfoContainer |
| Borders | BorderSubtle, BorderDefault, BorderStrong, BorderFocus |
| State layers | StateHover, StatePressed, StateSelected, StateFocused |
| Rarity | RarityCommon, RarityUncommon, RarityRare, RarityEpic, RarityLegendary, RarityMythic |
| Glows | GlowPrimary, GlowSecondary |
| Rows | RowLocatedBg, RowLocatedBd, RowOwnedBg, RowOwnedBd, RowStoredBg, RowStoredBd |

External themes with the same name as a built-in override the built-in.

## 10. The Runtime — Loader, Registry, IPC

### `PanacheTheme` — the immutable record

`src/Theming/PanacheTheme.cs`. C# `record` with `required` `PColor` for every v3 slot, plus
a `Name` and computed getters for every legacy V1 alias. Never construct one manually in
consumer code — get instances from `PanacheThemes.Active` or `PanacheThemes.Find(name)`.

### `PanacheThemes` — the static registry

`src/Theming/PanacheTheme.cs`. Owns:

- `Default` — the built-in fallback (currently the Shadow palette; field name is `Default`
  for legacy API reasons).
- `BuiltIn` — read-only list of built-ins. Currently `[ Default ]`.
- `External` — set by `ThemeLoader`, whatever's on disk.
- `All` — externals wins ties, but the built-in list is always considered — so `Shadow` is
  always in the picker.
- `Active` — the current one. Read this once at init, subscribe to `ActiveChanged`.
- `ActiveChanged` — fires whenever the active theme swaps (user picked a new one, or an
  external theme with the active name was reloaded).
- `ThemesChanged` — fires whenever `SetExternal` runs (folder rescan).

### `ThemeLoader` — the folder watcher

`src/Theming/ThemeLoader.cs`. Watches `<devPlugins>/Panache/Themes/` with a
`FileSystemWatcher` (recursive, `*.json`). Debounces filesystem events by 200 ms
(editors write atomically via rename, which fires N events per save). On any change:

1. Enumerate `Themes/*.json` (flat shape).
2. Enumerate `Themes/*/theme.json` (folder shape).
3. Sniff schema — reject anything that's not v3.
4. Parse each surviving file. Root has a `slots` object → slotted-shape parser; otherwise
   flat partial override.
5. Resolve `basedOn` → fall back to `PanacheThemes.Default` if missing.
6. Merge — every unset slot inherits from the resolved base theme.
7. Call `PanacheThemes.SetExternal(loaded)`.

Broken files log a warning and are skipped — one malformed theme file does not disable
the rest.

### `ThemeIpc` — the cross-plugin surface

`src/Theming/ThemeIpc.cs`. Registers five Dalamud IPC endpoints:

| Endpoint | Signature | Notes |
|----------|-----------|-------|
| `PanacheUI.Themes.List` | `() → string[]` | All registered theme names. |
| `PanacheUI.Themes.GetActive` | `() → string` | Current active theme name. |
| `PanacheUI.Themes.SetActive` | `(string) → bool` | Swap active; returns `false` on unknown name. |
| `PanacheUI.Themes.Get` | `(string) → Dictionary<string,string>` | Full palette as slot→hex map in the v3 vocabulary; keys camelCase (`surface0`, `primary`, `secondaryContainer`, `rarityEpic`, ...). |
| `PanacheUI.Themes.ActiveChanged` | `publishes string` | Subscribe to be notified when active theme swaps. |

Direct in-process consumers should just reference `PanacheUI.dll` and read
`PanacheThemes.Active` — IPC is for plugins that want looser coupling.

### `Theme` — legacy accessor

`src/Components/PanacheComponents.cs::Theme`. Static passthrough to
`PanacheThemes.Active.<slot>` for the most-common slots. Kept so pre-theming code that
reads `Theme.Base` keeps working. New code should follow the snapshot rule (§1) and read
v3 slot names directly.

## 11. Consuming a Theme

### C# — in-process (Panache itself, downstream plugins that reference `PanacheUI.dll`)

```csharp
using PanacheUI.Theming;

public sealed class MyWindow : IDisposable
{
    private PanacheTheme _theme = PanacheThemes.Active;

    public MyWindow()
    {
        PanacheThemes.ActiveChanged += OnThemeChanged;
    }

    private void OnThemeChanged(PanacheTheme t) => _theme = t;

    public void Draw()
    {
        // Read colors off the snapshot, not off PanacheThemes.Active every frame.
        style.BackgroundColor = _theme.Surface0;
        style.BorderColor     = _theme.Primary.WithOpacity(0.22f);

        // Or via the legacy V1 alias (still works — forwards to the v3 slot).
        style.BackgroundColor = _theme.Base;
        style.BorderColor     = _theme.Accent.WithOpacity(0.22f);
    }

    public void Dispose() => PanacheThemes.ActiveChanged -= OnThemeChanged;
}
```

### C# — via IPC (plugins that don't want to reference `PanacheUI.dll`)

```csharp
using Dalamud.Plugin.Ipc;

var list      = pi.GetIpcSubscriber<string[]>("PanacheUI.Themes.List");
var getActive = pi.GetIpcSubscriber<string>("PanacheUI.Themes.GetActive");
var getTheme  = pi.GetIpcSubscriber<string, Dictionary<string, string>>("PanacheUI.Themes.Get");
var changed   = pi.GetIpcSubscriber<string, object>("PanacheUI.Themes.ActiveChanged");

// One-shot: get current theme's palette.
var active   = getActive.InvokeFunc();
var palette  = getTheme.InvokeFunc(active);
var surface  = palette["surface0"];        // "#0F0E12" for Shadow
var primary  = palette["primary"];         // "#E05C9A"

// Live updates.
changed.Subscribe(name => Log.Info($"Theme is now {name}"));
```

Wrap IPC calls in `try/catch` — Panache may not be loaded.

Note: the IPC dict returns **v3 keys only** — legacy V1 keys (`base`, `accent`, ...) are no
longer emitted. IPC consumers must migrate to v3 keys.

### HTTP — via the RenderApi

If a debug UI or external tool needs the palette, `GET http://localhost:17779/themes`,
`GET /themes/{name}`, `GET /themes/active`. See `src/RenderApi.cs`.

## 12. Authoring a New Theme

**Preferred workflow — ColorSchemeCreator v3:**

1. Open ColorSchemeCreator, pick a harmony (or hit "Roll" for random), and roll until the
   rules bar is 28/28 PASS (or accept the "manual" tag for a hand-crafted palette).
2. Save the theme — the tool writes `themes/<Name>/theme.json`, `preview.png`, and
   `rules_report.txt`.
3. Copy the whole `<Name>/` folder into
   `<devPlugins>/Panache/Themes/`.
4. `FileSystemWatcher` picks it up within ~200 ms; no restart needed.
5. Confirm it registered: `/panacheui themes` in-game.

**Partial override — flat JSON file:**

Drop `Themes/MyOverride.json`:

```json
{
  "name": "ShadowRed",
  "basedOn": "Shadow",
  "primary": "#FF3060",
  "secondary": "#B92040"
}
```

Same live-reload behaviour. Every other slot inherits from `basedOn`. Use this for quick
experiments, not for production themes — you lose the OKLCH / rules validation.

**Hand-authored full theme without ColorSchemeCreator:**

Discouraged. If you must:

1. Copy an existing `Themes/Shadow/theme.json` as a template.
2. Change `meta.name` and `meta.schema_version = "3.0"`.
3. For each slot, pick an OKLCH `L`, `C`, `H` inside the range documented in §5.
4. Compute the hex — either use ColorSchemeCreator's `oklch_to_hex` in a REPL, or use any
   OKLCH picker (e.g. https://oklch.com).
5. Run through the rules table in §4 mentally — or better, drop the file into
   ColorSchemeCreator and hit "Validate".

## 13. The Shadow Default

The palette Panache ships with as of 2026-07-10.

| Property | Value |

| Constant | Value |

| Constant | Value |
